# 🔮 RAG SQL Assistant

A full-stack AI-powered application that lets users ask natural-language questions about their data and get answers using a combination of **Retrieval-Augmented Generation (RAG)** and **Text-to-SQL**. The project also includes a video recording/upload module (**ViMax**), secure authentication with MFA, and a modern React frontend deployed on AWS.

## 🧭 Overview

**RAG SQL Assistant** is a chat-based application where users can:

- Ask natural-language questions about structured (SQL) and unstructured (document) data
- Get answers generated by an LLM, grounded in real data via RAG and Text-to-SQL
- Record and upload videos (ViMax feature) stored securely on AWS S3
- Manage their account with secure authentication, including optional 2FA
- Use the app in **light or dark mode**, with more UI/UX features being added (multi-language support, notifications center, etc.)

The project was built as an end-to-end learning/production exercise covering AI engineering, backend API design, frontend development, and cloud infrastructure/DevOps.

## 🏗 Architecture

```
                        ┌─────────────────────┐
                        │        User          │
                        └──────────┬────────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     │                            │
              ┌──────▼──────┐             ┌───────▼────────┐
              │  CloudFront  │             │  Route 53 / DNS │
              │   (S3 CDN)   │             └─────────────────┘
              └──────┬──────┘
                     │  (Static React build)
              ┌──────▼──────┐
              │   S3 Bucket  │  ← Frontend (React/Vite build)
              └──────────────┘

                     │ REST API calls (HTTPS)
                     ▼
              ┌───────────────┐
              │      ALB       │  (Application Load Balancer)
              └───────┬───────┘
                      │
              ┌───────▼────────┐
              │  ECS Fargate    │  ← Django backend containers
              │  (Docker)       │
              └───────┬────────┘
                      │
      ┌───────────────┼─────────────────┬──────────────────┐
      ▼               ▼                 ▼                  ▼
┌───────────┐  ┌──────────────┐  ┌─────────────┐   ┌───────────────┐
│    RDS     │  │ ElastiCache   │  │  ChromaDB    │   │   S3 (video    │
│ PostgreSQL │  │    (Redis)    │  │ (Vector DB)  │   │   storage)     │
└───────────┘  └──────────────┘  └─────────────┘   └───────────────┘
                                          │
                                          ▼
                                  ┌───────────────┐
                                  │   Groq LLM API │
                                  │  (via LangChain)│
                                  └───────────────┘
```

**Request flow (chat/RAG example):**

1. User sends a question from the React frontend.
2. Request hits the ALB → routed to a Django container running on ECS Fargate.
3. Django decides whether the query needs **RAG** (unstructured knowledge) or **Text-to-SQL** (structured data), or an **Agent** that can use both plus other tools.
4. LangChain orchestrates: embeds the question, retrieves relevant chunks from ChromaDB, and/or generates SQL to run against PostgreSQL.
5. The relevant context + question is sent to the **Groq LLM API**.
6. The generated answer streams back to the frontend and is shown in the chat UI (and cached in Redis for repeated queries).

## 🖥 Backend (Django)

The backend is a Django REST Framework application exposing endpoints for:

- **Auth**: register, login, logout, refresh token, email OTP verification, TOTP (Google Authenticator) setup/verify/disable
- **Chat**: ask questions in "Quick Mode" (fast keyword/RAG based) or "Agent Mode" (multi-tool LangChain agent reasoning), with streaming responses
- **History**: view and clear past questions/answers
- **File Upload & Analysis**: upload CSV, Excel, PDF, images, Word, or text files and ask questions about them (with OCR support for images)
- **ViMax (Video)**: generate pre-signed S3 upload URLs, save video metadata, list/delete videos
- **Profile & Settings**: update profile info, manage TOTP-based 2FA

Key production concerns handled in the backend:

- **Redis caching** for repeated/common questions (significant speedup on cache hits)
- **Rate limiting** to prevent brute-force login attempts
- **Token blacklisting** so logged-out JWTs can't be reused
- Deployment via **Gunicorn** behind **Nginx** (EC2 phase) and later as a **Docker container on ECS Fargate** behind an **ALB**

## 🧠 AI / RAG Pipeline

The core AI feature lets users ask questions in plain English and get answers grounded in real data, rather than the LLM hallucinating.

### High-level RAG flow

```
Data (SQL rows / documents)
        ↓
   Chunking (LangChain text splitters)
        ↓
   Embeddings generated
        ↓
   Stored in ChromaDB (vector database)
        ↓
User question → embedded → similarity search in ChromaDB
        ↓
Relevant chunks + question → Groq LLM (via LangChain)
        ↓
Generated, grounded answer → streamed to frontend
```

### Why chunking matters
- LLMs have a limited context window — an entire database can't be passed in one request.
- Smaller, relevant chunks reduce token usage/cost significantly.
- Focused context improves answer accuracy versus dumping the whole dataset into the prompt.

### Two query modes
| Mode | Description |
|------|-------------|
| **Quick Mode** | Fast, keyword-based retrieval — optimized for simple, common questions |
| **Agent Mode** | A LangChain agent that can reason over multiple tools/steps (RAG + SQL + other tools) for more complex questions |

### Text-to-SQL
For questions about structured data, LangChain's SQL toolkit lets the LLM write and execute SQL queries against PostgreSQL directly, returning natural-language answers based on the real query results.

### Additional AI-adjacent features
- **Voice input** — browser Speech Recognition API lets users ask questions by voice
- **Text-to-speech** — answers can be read aloud using the Web Speech Synthesis API
- **File analysis** — uploaded documents/images can be analyzed and questioned, with OCR for image text extraction

## 💻 Frontend (React)

A single-page application built with React 19, TypeScript, and Vite, styled with Tailwind CSS.

### Key pages/routes
- `/login`, `/register`, `/verify-otp` – public auth flow
- `/` – Dashboard (stats + quick actions)
- `/chat` – main chat interface (Quick Mode / Agent Mode, voice input/output)
- `/history` – past questions/answers
- `/file-upload` – upload & analyze files
- `/vimax` – video recording and upload
- `/profile` – manage profile info
- `/settings` – manage 2FA (Google Authenticator)

### State management
- **Zustand** stores manage auth state, chat messages, and (in-progress) notifications, avoiding prop drilling and keeping components simple.

### UI/UX features
- **Dark / Light theme toggle** — implemented via a `ThemeContext` + Tailwind's class-based dark mode, with the user's preference persisted in `localStorage` and system preference auto-detected on first load. All pages (auth pages, dashboard, chat, history, profile, settings, file upload, ViMax) are fully themed.
- **Responsive design** — mobile-first layout with a collapsible sidebar
- **Multi-language support** *(in progress)* — planned i18n layer for English, Spanish, French, Hindi, German, Japanese, and Chinese
- **Notifications center** *(in progress)* — bell icon with unread-count badge, backed by a Zustand store with persistence

## 🎥 ViMax — Video Recorder Module

ViMax lets users record video directly in the browser and upload it to S3.

- Uses the browser's `getUserMedia` API to access the camera/microphone
- Recording is handled via **RecordRTC**, chosen after the native `MediaRecorder` API proved unreliable — particularly on **iOS Safari**, where recordings would silently fail with empty blobs
- Device/browser detection (iOS/Safari) is used to apply platform-specific recorder settings (e.g. forcing `video/mp4` and specific bitrates on iOS)
- On stop, the recorded blob can be **previewed**, **downloaded locally**, or **uploaded to S3** via a pre-signed URL issued by the Django backend
- Uploaded videos are listed with metadata (title, duration, size, created date) and can be deleted

> **Note:** Even with `RecordRTC`, iOS Safari's support for in-browser video recording remains inconsistent due to platform limitations. A native (React Native / Swift) implementation is being considered as a more reliable long-term solution for mobile recording.

## 🔐 Authentication & Security

- **JWT-based auth** (access + refresh tokens) using Django REST Framework SimpleJWT
- **Token blacklisting** on logout so refresh tokens can't be reused
- **Multi-Factor Authentication (MFA)**:
  - Email OTP (one-time password sent via email, expires after 10 minutes)
  - TOTP via Google Authenticator (QR code setup, 30-second rotating codes)
- **Rate limiting** on login to mitigate brute-force attacks (HTTP 429 responses)
- **CORS/CSRF protection** configured for the frontend domain
- Sensitive actions (like disabling 2FA) require re-verification with a valid code

## ☁️ AWS Infrastructure

The project was intentionally migrated in stages to build a deep understanding of AWS, moving from Railway → EC2 → ECS Fargate.

| Stage | Description |
|-------|-------------|
| **Railway (initial)** | Quick deployment for early development (frontend, backend, Postgres, Redis all on Railway) |
| **EC2 (learning phase)** | Manual deployment: SSH into an EC2 instance, install dependencies, run Django with Gunicorn + Nginx, connect to RDS/ElastiCache — to understand what's happening "under the hood" |
| **ECS Fargate (current/target)** | Backend runs as a Docker container on ECS Fargate behind an **Application Load Balancer**, solving the issue where each new task gets a new IP (which breaks static IP-based routing) |

### Core AWS services used
- **ECS Fargate** – serverless container hosting for the Django backend
- **ECR** – stores the built Docker images
- **ALB (Application Load Balancer)** – routes HTTP(S) traffic to healthy ECS tasks
- **RDS (PostgreSQL)** – managed relational database
- **ElastiCache (Redis)** – managed cache layer
- **S3** – hosts the built React frontend as a static site, and stores uploaded ViMax videos
- **CloudFront** – CDN in front of the S3-hosted frontend
- **IAM** – fine-grained permissions for services (e.g. pre-signed S3 URLs)
- **VPC & Security Groups** – network isolation between tiers (public ALB, private ECS tasks, private RDS/ElastiCache)
- **Route 53** – DNS management for the custom domain
- **ACM** – SSL/TLS certificates for HTTPS

### Notes on S3 + CloudFront for a React SPA
Because React Router handles routing client-side, direct navigation/refresh on non-root routes (e.g. `/chat`) returns a 404 from S3 by default. This is resolved by configuring **CloudFront custom error responses** (403/404 → serve `/index.html` with a 200 status) so the SPA can take over routing after the initial load.

## 🔄 CI/CD Pipeline

**GitHub Actions** automates the build and deployment process:

```
git push → GitHub Actions triggered
    │
    ├── Backend workflow
    │     ├── Build Docker image
    │     ├── Push image to Amazon ECR
    │     └── Update/redeploy ECS service
    │
    └── Frontend workflow
          ├── npm install
          ├── tsc -b && vite build
          ├── Sync build output to S3
          └── Invalidate CloudFront cache
```

This removes the need for manual deployment steps — every push to `main` results in an automatic, consistent deployment.

- Some pages may need further dark-mode polish as new features are added.
